# 0020. Парольний вхід, RS256 і refresh-сесії

- Статус: прийнято
- Дата: 2026-10-28
- Джерело: чат 2026-10-28; KIN-28, KIN-30
- Замінено: немає

## Контекст

Користувач явно погодив заміну 0005 для виконання призначених auth-тікетів. Google-вхід зберігається, парольний додається поруч. Цей запис приймає політику; наявність запису не означає, що реалізація вже завершена.

## Рішення

- Зберегти Google-вхід і Prisma Next; класичну Prisma schema не вводити.
- Додати парольний вхід.
- Access JWT: RS256, 15 хвилин, локальна перевірка підпису, issuer, audience, exp і scopes.
- Auth публікує лише відкриті ключі у JWKS. Ключі підпису зберігаються поза Git і переживають перезапуск.
- Невідомий `kid` відхиляється; локальний verifier сам не ходить у мережу. Завантаження та оновлення JWKS — обов'язок інтеграційного шару. Повна церемонія ротації ключів відкладена.
- Refresh: 30 днів, у сховищі лише хеш. Кожне успішне оновлення атомарно відкликає попередню сесію і видає нову. Logout відкликає сесію.
- Набір claims і глобальний user id мають бути узгоджені між Google та парольним входом; Google token не є providerUserId.
- Рішення 0005 замінено; його опис попереднього стану збережений як історія.

## Межі

Сховище refresh у браузері визначає 0025, першого admin і компенсацію реєстрації — 0021. Міжсервісний транспорт лишається gRPC згідно з 0003.

## Порушення

Зберігати refresh у відкритому вигляді; генерувати новий ключ на кожен рестарт; прибрати Google-вхід; відмовитися від Prisma Next без нового погодження.
