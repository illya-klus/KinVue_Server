# 0021. Параметри пароля, компенсація й перший admin

- Статус: прийнято
- Дата: 2026-10-28
- Джерело: чат 2026-10-28, явне погодження користувача; KIN-34, KIN-37, KIN-96
- Замінено: немає

## Рішення

- Argon2id: memoryCost 19456 KiB (19 MiB), timeCost 2, parallelism 1, hashLength 32 bytes, випадкова сіль 16 bytes для кожного пароля. Джерело: [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Параметри — публічна політика, не секрети. Пароль не обрізати й не логувати.
- Після вичерпання повторів реєстрації зберегти аудит-рядок `COMPENSATED`, очистити email і passwordHash, повернути 503. Той самий email може зареєструватися знову; лише ACTIVE може увійти. Це закриває G-09.
- Перший admin: локальна команда оператора за точним userId, яка підвищує лише наявну ACTIVE ідентичність. Публічного HTTP/RPC методу підвищення немає. Реєстрація завжди USER. Новий access token після повторного входу містить admin scope. Це закриває G-02.

## Процедура оператора

1. Отримати точний глобальний UUID уже зареєстрованого користувача й перевірити його особу поза публічним API.
2. На довіреному хості Auth виконати локальну команду підвищення за UUID. Команда має перевірити ACTIVE і змінити роль транзакційно; невідомий або неактивний UUID має завершуватися помилкою без створення користувача.
3. Записати операцію в операторський аудит без паролів і токенів. Користувач повторно входить, щоб отримати access-token з admin scope.

Сама команда та видача scope належать наступній реалізації Auth, а не цьому decision gate.

## Статус реалізації

Користувач погодив усі три пункти. Реалізація має дотримуватись їх; наявність рішення не означає завершення відповідних кодових тікетів. Старі рішення не замінює.
