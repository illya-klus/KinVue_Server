# Правила документообігу

Цей файл — канон. Його читають Cursor, Claude і Codex.

Короткі копії лежать у `AGENTS.md`, `CLAUDE.md` і `.cursor/rules/document-workflow.mdc`. Скіли:

- `.cursor/skills/document-workflow/SKILL.md`
- `.claude/skills/document-workflow/SKILL.md`
- `.agents/skills/document-workflow/SKILL.md`

Якщо коротка копія розходиться з цим файлом, виконай цей файл і в тому ж чаті виправ копію.

## Навіщо

Кожне рішення з чату лишається в репозиторії. Наступний агент бачить, що вже прийнято, що зроблено і що свідомо не зроблено. Прийняте архітектурне рішення не обходять мовчки.

## Цей репозиторій

Це бекенд KinVue. Веб-клієнт живе в окремому репозиторії. Сюди не додавай `apps/web` і не збирай фронтенд у цьому workspace. Див. [0010](decisions/0010-v1-stack-backend-repo.md).

## Де лежить план

- `doc/design/` — продукт і цільова архітектура, файли `00`–`26`. Читати з [doc/design/README.md](design/README.md).
- `doc/plan/` — покроковий план збірки.
- `doc/backlog/` — тікети. На дошці Jira вони вже є. Другий набір з цих файлів не створюй.
- `doc/architecture.md` — що вже є в коді.
- `doc/archive/jira-import/` — чорнові вигрузки. Це не вимоги.

Цільові межі сервісів береш із `doc/design/` і рішення [0008](decisions/0008-target-ingress-and-plan.md). Дірки з `doc/backlog/engineering/09-gaps-and-unknowns.md` не закривай сам.

## Перед зміною архітектури

Прочитай `doc/architecture.md`, `doc/status.md` і `doc/decisions/README.md`, якщо задача чіпає будь-що з цього списку:

- межі сервісів і те, хто є публічним краєм
- транспорт між сервісами (HTTP, gRPC)
- спільні контракти і proto
- сховище, схему даних, міграції
- автентифікацію і токени
- інфраструктуру, CI, менеджер пакетів

Якщо зміна суперечить рішенню зі статусом `прийнято`:

1. Зупинись. Не пиши код, який обходить рішення.
2. Назви користувачу номер, назву рішення і що саме зламається.
3. Продовжуй лише після явної згоди.
4. Згоду запиши новим рішенням. Старе познач `замінено` і додай рядок `Замінено: NNNN`. Текст старого рішення не витирай.

Невизначене в `doc/status.md` не є дозволом. Якщо в коді є заглушка, не закріплюй її як контракт.

## Що писати після чату

Пиши в кінці чату, до відповіді що роботу завершено, якщо в чаті було хоч одне з цього: рішення, відмова, відкладення, завершена робота, покинута робота.

| Що сталося                                     | Куди                                                      |
| ---------------------------------------------- | --------------------------------------------------------- |
| Будь-яке рішення, відмова або відкладення      | Дописати секцію в `doc/log/YYYY-MM-DD.md`                 |
| Рішення зобов'язує майбутню роботу             | Новий файл `doc/decisions/NNNN-slug.md` і рядок в індексі |
| Змінилась картина системи                      | Оновити `doc/architecture.md`                             |
| Щось дороблене, кинуте або свідомо не зроблене | Оновити `doc/status.md`                                   |

Журнал лише дописують. Минулі секції не переписують і не видаляють. Один файл на календарний день. Кілька чатів за день — кілька секцій підряд.

Окремий файл рішення потрібен, коли наступний агент має зупинитись, якщо зробить інакше. Дрібне локальне рішення лишається тільки в журналі.

Номер рішення — наступний після найбільшого наявного, чотири цифри. Slug латиницею через дефіс. Шаблон: `doc/templates/decision.md`. Шаблон журналу: `doc/templates/session-log.md`.

Статуси рішення: `запропоновано`, `прийнято`, `відхилено`, `відкладено`, `замінено`.

## Чого не писати

Секрети, токени, паролі і вміст `.env` у документи не потрапляють. Назви змінних можна.

Не вигадуй рішення, якого не було. Те, що лише видно з коду, познач рядком `Джерело: стан репозиторію`. Те, що користувач сказав у чаті, познач `Джерело: чат YYYY-MM-DD`.

## Git

Кожна зміна потрапляє на GitHub лише через pull request у `dev`. Коміт або пуш прямо в `dev` чи `main` не роби.

1. Онови `dev`: локальний `dev` має збігатися з `origin/dev`.
2. Створи гілку від `dev`.
3. Якщо зміни вже лежать у робочій копії `dev` або в локальних комітах поверх нього, перенеси їх на нову гілку до коміту. Локальний `dev` лиши таким, як `origin/dev`. Force push не роби.
4. Закоміть на гілці, запуш її, відкрий pull request у `dev`.
5. Без відкритого pull request робота не завершена.

CI/CD як обов'язковий шлюз ще не налаштований. Не блокуй pull request тим, що пайплайна немає, і не додавай пайплайн без окремого тікета.

## Порядок у кінці чату

1. Дописати журнал.
2. Якщо рішення зобов'язуюче — файл рішення й індекс.
3. Підправити `doc/status.md` і, за потреби, `doc/architecture.md`.
4. Переконатись, що нове рішення не суперечить іншому зі статусом `прийнято`. Якщо суперечить — старе має бути `замінено` в цьому ж чаті, і про це сказано користувачу.
