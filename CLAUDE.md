# Документообіг KinVue Server

Канон: `doc/AGENT.md`. Шаблони: `doc/templates/`. Якщо цей файл розходиться з каноном — виконай канон і в тому ж чаті виправ цей файл, `AGENTS.md` і `.cursor/rules/document-workflow.mdc`.

## План

Це бекенд. Фронтенд — окремий репозиторій, веб сюди не додають. Цільова архітектура — `doc/design/`. Що вже зібрано — `doc/architecture.md`. Тікети — `doc/backlog/`, дошка Jira вже є. Дірки з `doc/backlog/engineering/09-gaps-and-unknowns.md` не закривай сам. `doc/archive/` — не вимоги.

## Перед зміною

Прочитай `doc/architecture.md`, `doc/status.md` і `doc/decisions/README.md`, якщо задача чіпає межі сервісів, транспорт, контракти, сховище, автентифікацію, публічний API або інфраструктуру.

Якщо зміна суперечить рішенню зі статусом `прийнято`:

1. Зупинись. Не пиши код, який обходить рішення.
2. Назви користувачу номер і назву рішення та що саме зламається.
3. Продовжуй лише після явної згоди. Тоді додай нове рішення і познач старе як `замінено`.

Заглушка в коді не є контрактом. Див. розділ «Помічено» в `doc/status.md`.

## Після рішення в чаті

Кожне прийняте, відхилене або відкладене рішення допиши в `doc/log/YYYY-MM-DD.md`. Файл дня тільки доповнюють, історію не переписують.

Файл у `doc/decisions/` пиши лише для рішення, яке зобов'язує майбутню роботу. Онови індекс. Якщо змінилась картина системи — `doc/architecture.md`. Зроблене і не зроблене — `doc/status.md`.

Секрети, токени і вміст `.env` у документи не пиши.

Не видаляй записи журналу і не виправляй минулі рішення заднім числом.

## Git

Зміни здавай тільки гілкою від `dev` і pull request у `dev`. У `dev` і `main` не коміть і не пуш.

Якщо файли вже змінені на `dev`, створи гілку від `dev` і перенеси зміни на неї до коміту. Локальний `dev` лиши як `origin/dev`. Force push не роби.

Без відкритого pull request робота не завершена. CI/CD як шлюз ще немає: не пропускай pull request через це і не додавай пайплайн без окремого тікета.
